# 04 架構師方案（3 次獨立審查合併）

## 1. 審查發現
| 支持度 | 嚴重度 | 問題 | 共識建議 |
|---|---|---|---|
| 3/3 | 高 | `inventory(house_id)` + `shards` 各自成表，第二階段改部件必遷移；count 對不到記憶卡 | 第一天就用**通用帳本**：`items/grants(user_id, kind, item_id, …)`，kind ∈ house/part/shard（1/3 加 pack）；2/3 進一步做每筆一列 + state（stock/placed/dismantled）+ `landmark_id, at`，格子存該筆 id |
| 3/3 | 高 | 格子 `id` 直指房型，玩家藍圖/UGC 進來要改格式；PRESETS 與 houses.json 雙存 | 格子存命名空間字串：`sys:minnan` / 日後 `u:<uuid>`；藍圖 JSON schema v1 現在定；`data/houses.json` 為內容正本，kit.js 只解譯 |
| 3/3 | 高 | 規則前後端各寫一份必漂移 | `shared/rules.js` 純 ESM（無 three/DOM），Pages 與 Workers 同檔 import，單測只測它 |
| 3/3 | 中 | `updated_at` 後寫者勝，手機時鐘不可信 | 伺服器 `rev` 整數，PUT 帶 rev，不符 409 + 伺服器版，前端二選一 |
| 3/3 | 中 | Sprint 0–1 本機、Sprint 2 登入：本機存檔如何併入帳號未定 | 正式支援**訪客模式**，`store.js` 同一 API 雙 adapter（local/remote）；登入一次性匯入——分歧：1/3 全匯、1/3 只匯 grid 草稿庫存歸零、1/3 `POST /claim` 上傳帳本但排除 debug 標記 |
| 2/3 | 中 | 山區/離島無訊號打卡會丟 | 經濟操作走本機 `pending ops` 佇列、client 產 op_id、伺服器冪等重放（客端時間 24 h 內有效）；1/3 反對：第一版須線上 |
| 2/3 | 低 | 每日簽到伺服器判不了縣市；地標全量一次載入 | 1/3 `counties.json` point-in-polygon；1/3 bbox 粗判；1/3 `landmarks/<縣市>.json` 懶載 + version |

## 2. 架構提案（共識）
- 依賴方向：views(town/planner/geo/map/ui) → `store.js` → `shared/rules.js`；`kit.js` 只被 town 用；worker → rules。
- 資料所有權：內容（houses/landmarks/counties）歸靜態 JSON，建置期產出、執行期唯讀、帶 `data_version`；帳本、打卡、城鎮快照 + rev 歸 D1；localStorage 只放訪客正本/草稿/佇列/UI 偏好，登入後永不當庫存權威。
- 演進：第二階段 = 帳本加 kind:part + `blueprints(id, owner, source, status, json)`，格子引用 `u:`；第三階段 = grants 轉讓列（送房）、`relations`、blueprints.status 審核、`/share` 重用為互訪。
- 一人原則：無框架、無 ORM、無 build；規則單檔、store 單檔、worker 薄路由。
- **三方交接介面**（2/3 明確提出）：Cowork 產 `data/*.json`、`type_map.csv`、`featured.csv`、JSON Schema v1、`test_plan.md`；Design 產 `tokens.css`/`palette.json`、`ui_strings.json`（i18n/zh-TW）、`flows.md`、SVG；Code 消費上述產 `src/`、`schema.sql`、`wrangler.toml`。

```
data/*.json(唯讀) ─┐
shared/rules.js ───┼→ store.js ⇄ api.js ⇄ worker(D1: users/items|grants/checkins/towns.rev/ops)
kit → town / planner / geo / map / ui ──┘
pending ops →(上線)→ POST /ops 冪等重放 → items + town@rev
```
