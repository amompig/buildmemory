## B. 投票
1. 兩態（看／擺放）：gestures 少一個狀態、少一組文案；擺放中單指＝塗路或幽靈落房、雙指＝相機即可。
2. 日上限 30；accuracy 拒收 200 m：容差 `R+min(acc,50)` 已封頂，200 m 以上只會產生假 too_far，拒收反而訊息清楚。
3. 錯誤碼＋數值：`rules.js` 回 `{code, dist|until|retry_after}`，前端按鈕預檢與伺服器拒絕共用同一函式與同一句話。
4. Code 先打通 3 房型，Cowork 再抽 schema：schema 來自實物才不會改兩次。
5. 第一版不做：打卡要圖磚本就在線；只留 `op_id` 冪等欄。
6. 通用房 ×1 色票變體、上限 3：不加格子型別、不加規則；`kind=decor` 先開 enum 不發放。
7. 接受＋一處修改：離線開 App 允許編輯快取版，上線後走同一 409 流程；草稿 30 天只在本機。
8. 接受：mood enum、note 伺服器正規化 ≤40 字，存 grant 列，前端 `textContent`。
9. 保留 70%＋進度條：純 grid 函式，不需伺服器打卡計數當輸入。
10. 2 棟＋預鋪路：兩棟才練得到第二次放置與鄰路規則；贈品由伺服器發給 `device_id`，grid 首日就合法。

## C. 底線與提醒
1. **單一真相**：庫存只信伺服器 `grants`；規則只寫在 `shared/rules.js`；任何客端自報的庫存、身分、時間一律不信。
2. **渲染預算**：每房型一個 baked 幾何＋一個 InstancedMesh、單一 WebGL context；需要每棟獨立幾何或第二 context 的功能，Sprint 0 滿格量測通過前不排。
3. **Sprint 0 = 3–4 天、先 3 房型**；核心迴圈（畫路→放房→打卡→同步）沒跑通前，不碰 bloom、移軸、音效。

提醒整合者：每個新功能先回答「它落在 `grants` 列、grid 格、還是 `rules.js` 的哪一行？」答不出來的，就不是第一版。
